1. Executive Summary

ARAmane Arts is a web-based painting marketplace/application composed of three major parts:

  1. Customer frontend

    • React
    • Vite
    • React Router
    • Runs the public painting marketplace, authentication, cart, order submission, order tracking and account pages.

  2. Admin frontend

    • Separate React/Vite application
    • Provides dashboard, painting management, order management, metadata, FAQs, administrator management and maintenance mode.

  3. PHP backend API

    • Direct PHP endpoint architecture
    • MySQL database through PDO
    • Cookie/session-based authentication
    • Separate customer and administrator sessions
    • Email notifications through PHPMailer
    • Application-level IP rate limiting
    • SQL migrations for evolving the database schema

3. Technology Stack

Customer

The customer application is a Vite React SPA.

Current package dependencies include:

React
React DOM
React Router DOM
Axios
Vite
ESLint

The package currently declares React 19.2.8, React DOM 19.2.8, React Router DOM 7.18.3, and Vite 8.3.0.

The application code inspected for the main commerce flows primarily uses the browser's native fetch() API.

Admin

The admin application is a separate React/Vite project under admin/.

The two frontend applications are deliberately separated rather than being one React application with an admin namespace. The admin has its own route tree and its own session model.

Backend

The backend is:

PHP
MySQL
PDO
PHP sessions
PHPMailer
JSON HTTP responses

The database connection is created with PDO using a MySQL DSN and prepared statements with emulated prepares disabled.

External services / browser integrations

The customer login integrates Google Identity Services for Google Sign-In. The browser obtains a Google credential and posts it to the backend auth/user-login.php endpoint.

4. Architectural Style

This is not an MVC framework such as Laravel, Symfony, CodeIgniter, etc.

The backend uses a lightweight endpoint-per-file architecture.

For example:

GET  /api/paintings/list.php
GET  /api/paintings/get.php?id=123

POST /api/cart/add-item.php
POST /api/cart/update-item.php
POST /api/cart/remove-item.php

POST /api/orders/create.php
POST /api/orders/cancel.php

POST /api/orders/update-status.php

POST /api/paintings/create.php
POST /api/paintings/update.php
POST /api/paintings/upload-images.php

Each PHP file is effectively a route/controller.

There is no large centralized router deciding which application service to invoke.

The pattern is closer to:

HTTP request
    ↓
specific PHP endpoint
    ↓
shared common/auth/config includes
    ↓
validation
    ↓
SQL
    ↓
side effects
    ↓
JSON response

This makes the system relatively easy to trace feature-by-feature because the endpoint name usually corresponds directly to the UI operation.

The public customer application continuously checks:

The backend also has explicit maintenance endpoints:

11. Customer Authentication Architecture

The customer authentication backend uses a PHP session.

The common authentication file is:

api/auth/_common.php

It:

  • starts a PHP session
  • defines the session cookie
  • uses HttpOnly
  • supports Secure
  • supports configurable SameSite
  • configures CORS
  • allows credentials
  • parses JSON requests
  • provides common JSON response functionality
  • provides requireCustomer()

The customer session is named:

painting_marketplace_session

and authenticated users are identified through:

$_SESSION['user_id']
$_SESSION['user_type'] === 'customer'

This is cookie/session authentication, not a JWT/bearer-token architecture.

22. Order Submission Architecture

This application does not treat the initial checkout as an immediate payment transaction.

The cart page clearly treats this as:

Pay Now

and is reviewed after submission.

The customer submits:

POST /orders/create.php

  "shipping_email": "...",

24. Server-Side Order Creation Pipeline

The backend flow is:

POST /orders/create.php
        ↓
require customer
        ↓
read JSON request
        ↓
validate shipping/contact fields
        ↓
status = PENDING_ACCEPTANCE
        ↓
BEGIN TRANSACTION
        ↓
lock current cart rows FOR UPDATE
        ↓
load paintings
        ↓
validate paintings are active
        ↓
validate quantities
        ↓
resolve selected painting size
        ↓
resolve standard size if none selected
        ↓
calculate unit price
        ↓
calculate base amount
        ↓
generate order number
        ↓
INSERT orders
        ↓
INSERT order_items
        ↓
INSERT order_status_history
        ↓
DELETE cart items
        ↓
COMMIT
        ↓
send email notifications
        ↓
return JSON 201

This exact structure is implemented in api/orders/create.php.

25. Why FOR UPDATE Matters in Order Creation

The order creation query uses:

FOR UPDATE

while reading cart rows.

This means the transaction locks the affected cart rows while the order is being built.

Conceptually:

Cart read
    ↓
row lock
    ↓
price/availability calculation
    ↓
order insert
    ↓
cart deletion
    ↓
commit

This is designed to reduce race conditions around concurrent order submission.

26. Order Pricing Model

The backend currently resolves the price roughly in this order:

Selected size option exists?
        │
        ├── YES → use size option price
        │
        └── NO
              ↓
       standard size option
              ↓
       if still unavailable:
              ↓
       discount_price if valid
              ↓
       otherwise base price

The order then stores its own pricing values.

The SQL insert includes fields such as:

subtotal
base_amount
customization_amount
shipping_amount
delivery_amount
discount_amount
total_amount

At the current order creation path:

customization_amount = 0
deliveryAmount = 0
discountAmount = 0

totalAmount = baseAmount

The exact implementation is in api/orders/create.php.

27. Why Order Items Store Size Information

When an order item is created, the backend stores not merely:

painting_id

but also snapshot-like size information:

size_option_id
size_name
size_width
size_height
size_unit
painting_name
quantity
unit_price
total_price

This means historical orders retain the relevant pricing/size information even if a painting's current configuration changes later.

The database evolution for this feature is reflected in the migration sequence:

004_painting_size_options.sql
005_cart_item_size_option.sql
006_order_contact_and_size.sql
007_dedupe_painting_size_options.sql

28. Order Number Generation

The backend creates an order number in the form:

ORD-<random hexadecimal value>

It uses random bytes rather than relying only on the database numeric ID.

So there are effectively two identifiers:

database order ID
order number shown/communicated to users

29. Order Status History

Every important status change is recorded separately in:

order_status_history

Initial order creation creates:

old_status = NULL
new_status = PENDING_ACCEPTANCE
changed_by = customer user ID
changed_by_type = USER
notes = "Initial order request"

This creates an audit-style timeline for the order.

30. Cart Cleanup After Order Creation

After successfully creating:

orders
order_items
order_status_history

the backend deletes the user's cart items and commits the transaction.

Therefore:

Cart
  ↓
Order
  ↓
Cart emptied

The cart is not left as the permanent copy of the order.

The order tables become the authoritative historical representation.

31. Order Creation and Email Notifications

Only after the transaction commits does the backend call:

sendNewOrderNotifications(...)

This is an important sequencing decision.

Conceptually:

Database transaction
        ↓
COMMIT SUCCESSFULLY
        ↓
send email notification

rather than:

send email

33. Customer Cancellation

The customer cancellation request is:

The backend:

  1. Requires customer authentication.
  2. Looks up the order belonging to that customer.
  3. Locks the order with FOR UPDATE.
  4. Checks current status.
  5. Changes the status to CANCELLED.
  6. Inserts status history.
  7. Commits.
  8. Sends a status notification.

34. Current Cancellation Rule

The current backend blocks cancellation when status is:

CANCELLED
PAID
PROCESSING
DISPATCHED
DELIVERED

Therefore, according to the current implementation:

PENDING_ACCEPTANCE → cancellable
ACCEPTED           → cancellable
PAYMENT_DUE        → cancellable
REJECTED           → cancellable
PAID               → not cancellable
PROCESSING         → not cancellable
DISPATCHED         → not cancellable
DELIVERED          → not cancellable
CANCELLED          → not cancellable

This is an important implementation detail.

In particular, REJECTED is currently not blocked by cancel.php. If the intended business rule is that once an artist rejects an order the customer must never be able to cancel it, the current backend does not yet enforce that rule.

62. Rate Limiting

There is an application-level rate limiter:

The current rules are:

Authentication endpoints:

The painting list endpoint is deliberately excluded from rate limiting.

CORS preflight requests are excluded.

Already authenticated and 2FA-verified administrators are excluded.

The limiter uses files in the operating system's temporary directory rather than storing counters in the repository.

The basic concept is:

    ↓

    ↓

    ↓

to protect concurrent access.

If the server cannot create/open the temporary rate-limit file, the implementation intentionally fails open.

In other words:

        ↓

rather than:

        ↓

This is explicitly documented in the source.

99. Bottom Line

The repository is built around a straightforward three-application architecture:

CUSTOMER REACT APP
        +
ADMIN REACT APP
        +
PHP / MYSQL API

The API is the central authority.

The most important domain is the order lifecycle:

Cart
  → Order Request
  → Pending Acceptance
  → Admin/Artist Decision
  → Payment Due
  → Paid
  → Processing
  → Dispatched
  → Delivered

with:

order_items
order_status_history
transactional updates
email notifications

forming the backbone of the commerce logic.

The authentication model is session-based, with separate customer and admin sessions; admin operations additionally require verified 2FA state.

The repository also already contains the foundations for:

multi-size paintings
image galleries
SEO metadata
Google login
password reset
maintenance mode
email notification groups
rate limiting
order history
administrator management

The principal implementation issue visible from this source review is that some behavior still needs to be formalized at the business-rule level, especially the exact order state transition rules and rejected-order cancellation behavior.
